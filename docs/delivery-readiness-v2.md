> 上一版此处写着「ubuntu 因一个偶发用例失败」，并把它归因于重启竞态。**那个判断是错的**，
> 修正记录留在这一节里，因为「当时为什么看错」比结论本身更有用：
>
> 失败现象是 `WorkerCrashedError: plugin worker echo died (code=1)`——新 worker 成功报告
> 5 个命令，12ms 后死于第一次调用。真因是子进程给自己设的 `RLIMIT_NPROC = 64`：它按
> **真实 uid 全系统**计数，而且把**线程**也算进去。CI runner 上整个账号共享这份配额，
> worker 第一次 `run_in_executor` 创建读帧线程时就可能撞上 `can't start new thread`，
> 异常逃出主循环 → 进程以 1 退出。账号当时有多忙决定了它是「偶发」还是「必现」，这正是
> 它看起来随机的全部原因；而 `RLIMIT_NPROC` 是 POSIX 专有，Windows 任务永远看不到。
>
> 为什么查了这么多轮：子进程的 stderr 只进了 DEBUG 日志，而 Python 在未捕获异常退出时
> 恰好只把 traceback 写到 stderr——唯一能解释failure的那行被丢了，宿主只剩一个数字。
> 现在 worker 保留最近 40 行 stderr（脱敏），崩溃消息与 ERROR 日志都带上它；读循环里
> 的环境性失败也会变成一帧 `fatal` 上报，而不是静默退出。
>
> 同样的错误还有第二处：`RLIMIT_AS = 256 MiB` 计的是**虚拟**地址空间，裸 CPython 在跑
> 任何插件代码前就已占用数百 MB，于是连一个 8MB 线程栈都可能放不下。已提到 512 MiB，
> 并在 `isolation.py` 里定义为唯一常量，避免loader/supervisor/runner 三处再次漂移。

## 一、这一轮新增了什么

### 1. 分句渐进发送（流式）

QQ 没有消息编辑接口，OneBot v11 与官方 API 都不提供，所以「气泡里逐字刷新」在这个
协议上无法表达。能用的是**多条消息**。因此这里的流式定义为：模型还在生成时，第一句
完成就发出去，后续按节奏跟上。

三条规则是**强制**的，不是期望：

| 规则 | 为什么 |
| --- | --- |
| 在 `。！？…` 与 `. `（句点后跟空格）切分 | 中文无词间空格，句号无歧义；英文必须要求后续空格，否则 `3.14`、`example.com` 会被切成两条消息 |
| 单句超过字符预算时在最近的逗号/空格处切 | 模型偶尔不写句号 |
| 累计超过 `first_packet_deadline` 仍无完整句，就把已有内容发出去 | 否则慢模型的「首条消息延迟」等于「总延迟」，流式的唯一收益归零 |

**失败策略**（半句话发出去就收不回来）：provider 在**首句之前**挂掉 → 回落为普通
单条调用；**首句之后**挂掉 → 保留已发送的片段并记录中断，而不是再补一条完整答案。

开关：`SOAPBOT_STREAM_REPLY`（默认关）。默认关的理由是它会改变群里收到的消息**条数**，
这是行为变更，应由运维主动打开，而不是部署后自己数出来。适配器还必须声明
`Capability.PROGRESSIVE`，官方 QQ 的被动回复窗口不允许第二条消息，因此不支持者自动
退化为单条。

控制台「09 流水线追踪」已可读取 `chunks` 与 `stream` 字段（首 token、首发送、中断标记）。

### 2. 插件市场：安装 ≠ 批准

这是本轮最关键的边界。若上传即批准，「上传一个文件」就成了完整的提权路径。

`plugins/installer.py` 只落地字节，**从不写批准记录**，并且每种恶意包都对应一条防线：

| 攻击 | 防线 |
| --- | --- |
| `../../etc/cron.d/x` | 每个解压路径规范化后必须落在目标目录内，越界即拒 |
| 绝对路径 `/etc/passwd` | 直接拒绝 |
| 符号链接指向树外 | 拒绝 symlink 条目 |
| zip 炸弹 | 按**实际写盘字节**计数（不信任头部声明），超限即中断 |
| 海量小文件 | 解压前先查条目数上限 |
| 清单不在单层根目录 | 拒绝，不猜布局 |
| 包内两个 `plugin.yaml` | 拒绝 |
| 先装后改清单提权 | 批准以 `manifest_digest` 为准，摘要由服务端从落盘字节重算 |
| 中断留下半个目录 | 先解压到 staging，校验通过后原子移动；失败留旧版本完好 |

控制台新增第 11 页「插件市场」：上传区明确写「安装后仍需逐项批准」，能力按风险分三档
（颜色 + 文字标签，色盲可用），空状态给出 `data/plugins/` 的目录树，覆盖无法上传的场景。

### 3. MCP 工具汇入同一张工具表

两个决定偏离了「显而易见」的做法，理由都写在代码里：

1. **没有引入官方 SDK**。这里实现了实际用到的四个调用（`initialize` / `tools/list` /
   `tools/call`），走 stdio 换行分隔 JSON-RPC。MCP 服务端按定义是第三方代码，解析面越小
   越可审；为可选能力引入并锁死一棵依赖树不划算。将来若需要 sampling / roots / prompts，
   那时再换 SDK 才是对的，本模块就是那时要删的东西。
2. **MCP 工具进 `PluginToolRegistry`，不开第二条通道**。否则 MCP 工具会有自己的一份
   鉴权代码，而被忘掉的那一份就是被利用的那一份。

命令必须是 **argv 列表**并以 `execve` 启动、经 PATH 解析，永不经过 shell；配置里写成字符串
会被直接拒绝——字符串必须被切分，而切分正是引号把「读文件」变成「执行命令」的地方。
`min_role` 按服务端配置，每次请求都过滤；角色名写错按 anonymous 处理（失败即收紧）。

服务进程由 runtime 持有：重启机器人不会留下孤儿进程；某个服务起不来只降级为「没有外部
工具」，不会拖垮整个进程。`GET /api/mcp` 报告每个服务与工具数（含失败原因，因为「0 个工具」
和「服务崩了」是同一张空列表，但修法相反）。

### 4. 语音：两个方向都失败开放为文本

入站走 Provider 的 `transcribe` 槽位（与 chat/embed 同一套 router，带降级与故障转移），
出站用 `edge-tts`，作为**可选**依赖 `[voice]`——语音是单一厂商的网络客户端，绝大多数部署
永远不会调用它。

两个决定值得单独说：

**音频 URL 是攻击者给的。** 群成员发一条语音，协议交给我们一个 URL，由服务器带着自己的
网络位置去取。若不检查，「发语音」就变成了「让服务器访问 `169.254.169.254`」——云上
IAP/metadata 凭证窃取的标准手法。所以 URL 先解析、解析出的地址必须是公网（`is_global`
一次覆盖 loopback/private/link-local/reserved），且 **不跟随重定向**——否则公网 URL 可以
先通过检查再 302 到内网。

**失败绝不用编造的内容填补。** 转写失败 → `[语音]`（所有人可见的缺口）；合成长文本失败
或依赖缺失 → 发文本，并在日志里说明原因。让模型「猜一段语音说了什么」，等于把从没人说过
的话记在这个用户名下——比一个缺口糟得多。同理，语音段发送失败会**再发一次文本**，否则群
里收到的是一条都没有，看起来就是机器人挂了。

### 5. 可运维面

- `GET /healthz`：存活探针（与 `/api/health` 同一事实，两个名字是因为容器 healthcheck 与
  各家反代的默认期望不同）。
- `GET /readyz`：就绪探针。只检查「让它无法工作」的事——数据目录不可写（SQLite 会先在这里
  表现出来）、请求了运行时却没构建起来、或构建了但没在跑。**不**因为某个 QQ 号离线就返回
  503，那会把控制台从负载均衡里摘掉，恰好是运维最需要它的时候。
- `scripts/backup.py`：用 `sqlite3.Connection.backup` 取一致性快照（服务以 WAL 运行，
  `cp` 出来的库可能缺最后几条已提交的消息），含 `data/soapbot.db` + `config/` + manifest，
  先写临时文件再改名。
- `scripts/restore.py`：先读 manifest 校验 `schema_version`（高于当前程序直接拒绝，而不是
  恢复后崩在迁移上），拒绝越界条目，旧库改名为 `soapbot.db.pre-restore-<时间戳>` 而非覆盖。

## 四、剩余工作（按建议顺序）

1. **多语言**（阶段 6）：只翻译**面向使用者**的文案（界面、机器人回复模板、API 的 `detail`），
   日志保持英文——同一事件在不同语言下变成不同字符串会破坏 grep 与告警规则。
2. **系统设置页**（第 12 页）：语言、语音开关、MCP 状态与重连。语音的两个开关目前只能通过
   环境变量设置，没有界面入口。
3. **真实语音链路实测**：转写槽位由 mock provider 验证过（含 URL 拒绝与降级），但**没有接**
   真实的 STT 厂商端点，`edge-tts` 也只验证了「依赖缺失时明确报错」这一条路径。
4. **数据库迁移**：当前 `SCHEMA_VERSION = 1`，尚无 v2。迁移器在真正需要 v2 时再写——
   现在写一个没有迁移步骤的框架，属于「声明了但没接线」，与本项目规则冲突。
