八个阶段

纵向箭头是硬依赖；虚线框是贯穿约束，不是阶段
  1. 1

    交付阻断解除

    未启动

    首次提交、分支与 CI 对齐、清理残留空目录与构建临时产物、补 py.typed、补 soapbot token 子命令、社区文件。

    为什么排第一：仓库零提交时，其余七个阶段的「已验证」全部无法被他人复现。 另外 CI 只在 main 触发而本地是 master，等于 800 项测试没有执行点。

    验收门 git log 有提交 · git status 干净 · CI 在目标分支真实跑通 · 无 data/ 的干净副本 pytest 不退化
  2. 2

    流式输出贯通

    未启动

    SentenceAggregator 纯函数聚合器 · respond_stream() · ModelStage 仅末轮分支 · ReplyStage 分句发送 + 复用 core/ratelimit · 追踪页展示分句序列。

    形态是分句渐进发送而非逐字刷新：OneBot 与 QQ 官方都不提供消息编辑接口， 逐字只能靠撤回重发，结果是刷屏且撞 5 msg/s 限频。首包上界 1.2s——否则模型吐字慢时 首包延迟等于总延迟，流式收益归零。

    验收门 单测证明分段与首包上界 · 真实 OneBot mock 端观察到多条按序到达 · STAGE_ORDER 未变（不新增 Stage）
  3. 3

    插件市场

    未启动

    plugins/installer.py 六类攻击防护 · POST /install · 11 页市场界面（卡片、上传、能力风险分级、安装后引导批准）。

    安装 ≠ 批准，是两个动作。若安装顺手批准，上传一个包就等于获得其声明的全部能力， 而「改 manifest 加能力必须重新审批」这条既有防线会从侧面被绕过。

    验收门 六类恶意包（zip slip / 压缩炸弹 / 多插件包 / 路径歧义 / digest 伪造 / 越界符号链接） 全部被拒 · 正常包安装后出现在列表且未被批准
  4. 4

    MCP 客户端

    未启动

    mcp/client.py 连接与握手 · mcp/config.py 只允许显式声明的命令 · 工具汇入 PluginToolRegistry · 状态查询接口。

    必须与插件工具汇入同一张表、走同一次权限过滤。另开旁路的直接后果是 MCP 工具绕过角色校验，于是「能力逐项授权」在不同工具来源上口径不一。

    验收门 MCP 工具出现在 available_for(principal) 返回值中 · 越权角色看不到（wiring 测试，非注册表自测）
  5. 5

    语音入站与出站

    未启动

    STT 走 BaseProvider.transcribe 新槽位（不引本地模型）· TTS 作为可选依赖 [voice] · 适配器不支持 RECORD 时降级为文本。

    SegmentType.RECORD 与 Capability.RECORD 早已预留但无人使用—— 这正是「声明了但没接线」的典型。要么接上，要么删掉声明。

    验收门 不支持 RECORD 的适配器正确降级 · TTS 依赖缺失时报明确错误而非静默 · 语音消息转写后进入同一对话上下文
  6. 6

    多语言

    未启动

    后端标准库 gettext + JSON 目录 · 前端自研 t() + 响应式 locale · 12 页系统设置（语言、语音、MCP 状态、运行时信息）。

    只翻译面向使用者的文案，不翻译日志。日志是给运维做关键字搜索的， 同一事件在不同语言下变成不同字符串会破坏搜索与告警规则。

    验收门 切换语言后界面与对外回复变化 · 日志保持英文 · 缺失 key 回落中文并记 warning
  7. 7

    可运维面

    未启动

    /healthz 存活 · /readyz 就绪（DB 可写、配置可读）· DB 版本迁移 · scripts/backup.py / restore.py · UPDATING.md。

    「可运维」的判据不是有文档，而是备份→清空→恢复后数据一致。 没有可执行的恢复演练，备份脚本只是心理安慰。

    验收门 /readyz 在 DB 不可写时返回非 200 · 备份恢复后数据一致 · 迁移可从 v1 升到当前版本
  8. 8

    评估报告 v2 与全量回归

    未启动

    docs/delivery-readiness-v2.md 反映当前状态 · 保留旧报告作历史 · 依赖安装实测（clean venv）· 全量测试、lint、类型、构建、对比度。

    旧报告记录的是修复前的状态，且明确声明「不随后续改动重写」。 在它上面改数字会销毁问题清单的证据价值，所以新开一份。

    验收门 全新 venv 从 pyproject.toml 安装成功且能启动 · 全量测试不退化 · 每条结论都有可复现命令

贯穿约束（不是阶段，无法被勾掉）

容器部署

静态检查通过 · 实测未验证

已做：新建 scripts/check_deploy.py 做静态核验，14 项全过， 并接入 make deploy-check 与 tests/test_deploy_config.py（11 项）。 它抓出并修掉了两个会导致 compose up 直接失败的真实缺陷：

  • 容器内绑定 127.0.0.1 却声明了 ports: —— 端口映射指向容器 eth0，而服务只监听容器自身 loopback，宿主机永远连不上。已改为容器内 0.0.0.0，隔离仍由宿主机侧 127.0.0.1:6185 保证。
  • ./secrets/master.key 挂载源不存在，且该文件被 .gitignore 排除（*.key）—— 全新 clone 后 Docker 会在此路径创建一个空目录， 应用读目录当密钥文件失败，然后静默退化为明文存储插件密钥， 而容器仍报告 healthy。已改为默认注释掉并写明启用步骤。

为什么仍标「未验证」，以及本机 Docker 为什么装不上（实测记录）： docker 命令不存在 → winget install Docker.DockerDesktop 下载与哈希校验成功，但安装程序需 UAC 提权，退出码 4294967291（0xFFFFFFFB）→ 当前账户 IsAdmin = False；wsl --status 报未安装发行版； CPU VirtualizationFirmwareEnabled = False；系统为 Windows 11 家庭版， 不支持 Hyper-V。四条相互独立，非配置可绕过。

解除条件 云服务器上：配好镜像加速（本机实测 Docker Hub 直连超时， docker.m.daocloud.io 走 token 流程可取到 manifest）→ 构建成功 → id -u 为 10001 → 只读根下 /data 可写 → /api/health 返回 ok → healthcheck 转为 healthy

详细步骤与四项判据命令见 deploy/daemon-mirror.md。

三条不可让步的规则

已完成
  • 文档与代码冲突时改文档并写明理由，不得默默放宽（既有先例：§6.1 对配置写入的修订）。
  • 未接线的能力等于不存在，每个新能力必须有 wiring 测试，禁止只测注册表。
  • 不假装修了：未实测的标为未验证，比声称通过更可信。

为什么 2–6 不并行

已完成

逻辑上 P2–P6 相互独立，但P3 与 P4 共用同一张工具注册表 （插件工具与 MCP 工具必须汇入同一处过滤），同时改会互相冲突； P5 要改 stages.py 与 providers/base.py，与 P2 重叠； P6 要扫全站文案，必须最后做。串行是为了让每一步的「已验证」站得住。
