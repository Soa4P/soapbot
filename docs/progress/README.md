# 开发进度看板

用于查看「soapbot 可视化操作台」这一轮改造的完成度。不是产品的一部分，不进控制台，不占导航编号。

## 查看

```bash
python -m http.server -d docs/progress 8099
# 打开 http://127.0.0.1:8099/
```

**必须走 HTTP。** 双击 `index.html` 用 `file://` 打开会看到报错条，因为浏览器以 CORS 为由拦截 `file://` 页面发起的 `fetch`。看板会把这条原因直接显示在页面上，而不是留一片空白。

## 为什么不用框架

`docs/progress/` 是三个文件加一份 JSON，没有构建步骤、没有 CDN、没有 webfont、也没有 Tailwind。理由不是「简单」，而是项目已经有一条规则：`scripts/check_deps.py` 把依赖清单当作审计面，此前刚移除了四个声明但未使用的包。为一个内部看板引入构建链会直接破坏这条规则，而看板受益为零——它要的是「打开就能看」。

## 数据契约

唯一数据源是同目录的 `progress.json`。三级结构：

```
phase (阶段) → task (子任务) → files (文件清单)
```

- **状态枚举**：`todo` 未启动 / `doing` 进行中 / `done` 已完成 / `blocked` 受阻
- `blocked` 必须在 `note` 里写明原因（例如 `mypy` 基线 42 个错误这类「已知不修」的事）
- `current` 回答「现在在做什么、做到哪一步」；所有任务都不在进行时置 `null`，看板显示「当前无进行中任务」

### 百分比是算出来的，不是填出来的

```
子任务权重     = 该任务的文件数（无文件列表时按 1 计）
子任务完成比   = 已完成文件数 / 总文件数
整体百分比     = Σ(权重 × 完成比) / Σ权重
```

阶段百分比同理，只在本阶段内求和。

所以一个「4 个文件改了 3 个」的任务贡献 0.75，既不会显示成 0（全部没动），也不会显示成 1（做完了）。**看板没有手工填写进度的入口**，这是设计决定：手填的百分比没有可信度，而一个不可信的看板比没有看板更糟——它会让人以为情况已经被掌握。

## 防「看板撒谎」的三道措施

1. **陈旧检测**：`updated_at` 距今超过 **10 分钟**，页面顶部整体标黄并写明「最后一次更新于 …，以下是当时的进度，不代表现在」。一个停在三天前却显示「进行中 40%」的看板比没有看板更糟，因为它看起来是可信的。
2. **失败要显式失败**：`fetch` 失败时显示红色错误条与「重试」按钮，**保留上一次成功渲染的内容**并标注读取时间。不渲染空看板——空白会被读成「什么都没做」，那是另一个论断。
3. **只陈述四态，不猜**：不存在「大概完成」「基本可用」这类表达。

## 维护协议

每完成一个文件、或跨过任务边界，就更新 `progress.json`：

1. 改对应 `files[].status` 与 `tasks[].status`（任务内所有文件都 `done` 时才把任务置 `done`）
2. 更新 `current` 指向正在做的任务与具体步骤；停下来时置 `null`
3. **必须更新 `updated_at`**

第 3 条不能省。看板的可信度完全建立在这个时间戳上：忘了更新它，看板就会在第一小时后开始标黄，这是它应有的反应，而不是 bug。

## 维护者自查

每次收尾前问三个问题：

- 有没有哪个任务在 `progress.json` 里是 `done`，但对应文件其实没写？
- 有没有刚创建的文件没进 `files` 清单？
- `current` 指向的那一步，是不是真的正在做？

三个问题里任何一个答不上来，就先改 JSON 再继续。
