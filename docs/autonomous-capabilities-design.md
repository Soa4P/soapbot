# 自主能力设计：看屏幕（自助玩游戏的前置）与自主挑音色

> 状态：**§1 第一阶段（看屏幕）已实现**（2026-11-14，见 §1.5 落地附记）；§2 挑音色的
> 管线环节未实现；**控制面（键鼠注入）未开工**，三前置不变。
> 放进来是因为两件事都需要「宿主先有受审能力面，插件才能申请」——与 `bilibili`
> 能力（#41）同一模式。
>
> 注意区分：本文的「看屏幕」是**本机屏幕画面**，单向进模型、不落盘。已经实现的
> `browse` 能力面读的是**公开网页**，遵守 robots.txt、无登录态、只交文本快照。
> 两者数据源、信任级别与验收门槛都不同，不是同一件事的两种实现。
>
> 人格卡里已可写 `voice_self_select` 这个开关（由 `ai/autonomy.py` 校验、随面板保存
> 与版本回滚保留），但**本文 §2 的挑音色管线环节仍未实现**：开关存在不等于能力存在，
> 在 voice-pick 落地前它不会改变任何行为。

## 1. 看屏幕：自助玩游戏的前置能力（改编自 dsh-see-now）

### 1.1 目标与硬边界

目标：机器人「自己看」一台**专门提供给它的电脑**的画面（变化帧筛选、拼图、进
上下文），为将来「完全自主控制这台电脑」打地基。dsh-see-now（Apache-2.0）给出
的三个可迁移机制：按变化量筛帧（静止几乎不花钱）、几帧拼一张图省 token、
运动量自适应采样。

硬边界（每一道都是设计门槛，不是实现细节）：

1. **专用机器**：截屏能力只对声明为「bot 工作机」的宿主开放（配置显式列出机器
   标识），绝不在操作者日常使用的机器上启用。
2. **画面是单向进模型的**：帧只进模型上下文（与图片进 pipeline 同一条路），不落
   盘、不进审计、不进插件 storage——画面里可能有一切隐私。
3. **帧数与频率配额**：`screen` 能力面 30 次/分钟滑窗 + 单次拼图上限（帧数×分
   辨率），超限是「说出原因的拒绝」，同 ModelQuota。
4. **只看，不碰**：第一阶段（本设计）**没有任何注入输入的能力**（不动键鼠）。控制
   属于第二阶段，需要另行设计并默认关闭。
5. **会话可见性**：机器人在哪个会话里「看了屏幕」，审计记哪条（时间+时长+帧数，
   不记内容）。

### 1.2 形态

- 宿主新能力 `Capability.SCREEN`（敏感+限频），宿主持有截屏执行器（mss/Pillow），
  插件只能「申请一帧拼图」，拿到的引用直接进上下文，插件代码摸不到位图本体。
- 控制面（键鼠注入）**不在本设计内**；实现前需要：机器物理隔离声明、操作者一键
  物理断连（硬件开关）、以及「机器人自己的操作日志可被操作者实时看到」三条都落
  地才开工。

### 1.3 验收门槛（实现前必须逐条可测）

- 未授权插件调 screen → 能力拒绝 + 审计；
- 非声明机器上的截屏请求 → 拒绝；
- 帧数据出现在任何日志/审计/异常文本 → 门禁失败（同 Cookie 的零命中标准）；
- 停用 screen 能力后，进行中的拼图请求立即失败。

## 2. 自主挑音色：bot 自己决定 TTS 音色

### 2.1 现状

语音回复已实装（edge-tts 可选依赖，第 12 页开关，音色可选）；音色目前是操作者
在面板里选的，人格卡可以按群覆盖 `locale`，但音色选择是静态的。

### 2.2 设计：让 bot 挑，但挑得可审计、可回滚

- **决策发生在管线内，不是插件里**：音色是宿主语音回复的一部分，加一个轻量
  「voice-pick」环节——人格卡声明一段「我的音色自述」（想要的音色气质），管线把
  它与候选音色表（edge-tts voices，宿主启动时拉一次并缓存）一起交给模型选一个，
  结果写进 trace 与只读面板。
- **预算**：挑音色不是每条消息都挑——按人格 + 会话记忆一次挑选、缓存复用，
  人格变更时重挑。避免每条语音多一次模型调用的成本。
- **候选集是宿主给的**：模型只能从候选表里挑，不能捏造音色名；挑中的音色进
  trace，操作者可一键改回手动指定（手动指定优先于自主挑选）。
- **插件不做这件事**：TTS 是宿主语音面；做成插件意味着把「说出来的声音」交给
  capability 白名单之外的代码——违背「说出来的东西归管线管」的既有边界。

### 2.3 验收门槛

- 未配置 edge-tts（可选依赖缺失）时，自主挑选静默跳过，文字回复不受影响；
- 挑选结果与理由进 trace（第 09 页可看）；
- 操作者手动指定音色后，自主挑选不再生效；
- 一次挑选的 token 成本 ≤ 一次轻量对话（候选表是列表不是全量文档）。

## 3. 与扩展政策的接口

两条都属于「宿主先有受审能力面」的路径，与 bilibili 能力（#41）同模式：插件申请
能力、宿主持有执行器与凭据、审计只记元数据。实现顺序建议：挑音色（小、无凭据面）
先于看屏幕（大、凭据级敏感）；自助玩游戏的控制面排在两者之后，且按 1.4 的三条
前置条件单独开工。

### 1.4 第二阶段技术参考（dsh-cua 复核，2026-11-13）

[Mrkennyhungry/dsh-cua](https://github.com/Mrkennyhungry/dsh-cua) 是「控制面」的完整
实现层参考（Windows UIA 控件树 + 本地 OCR + 窗口绑定 + 受控浏览器 + 视觉语义）。
其 [data-boundary.md](https://github.com/Mrkennyhungry/dsh-cua/blob/main/docs/data-boundary.md)
的数据边界纪律与本仓库同源，四条直接进本设计：

1. **截屏只落本地**：帧不自动上传，进入模型上下文即销毁（与 §1.1 第 2 条一致）。
2. **caption 是唯一的「画面出机」点**：图标语义识别可配 key、可关、关闭时纯本地——
   soapbot 的对应形态是把「画面语义化」交给已有管线（vision 槽），不另开旁路。
3. **CDP 端口自认不是隔离**：本机任何进程都能附着浏览器会话——对应本设计的
   「专用机器」前置：控制面浏览器必须跑在独立系统用户下、用不保留登录态的
   临时 profile（dsh-cua 自己也是这么建议的）。
4. **kernel-boot.json 明文 token 的必要性自述**：高权限计划任务要读——soapbot 的
   对应物是「控制面凭据用文件而非环境变量」（同 MASTER_KEY_FILE 先例），且权限
   收紧到当前用户。

技术选型参考：UIA 控件树优先于纯视觉 OCR（结构化、可断言、不吃 token），OCR 只做
UIA 覆盖不到的自绘界面回退；窗口绑定（只操作声明过的窗口）对应本设计「专用机器」
边界的窗口级细化。**控制面（键鼠注入）开工三前置不变**（§1.1 第 4 条 + 三条落地
条件），本节只登记技术路线，不改变默认关闭的立场。

### 1.5 第一阶段落地记录（2026-11-14）

§1 的五条硬边界逐条兑现（`screen/capture.py`、`screen/inbox.py`，测试
`tests/test_screen_capability.py` 20 项）：

1. **专用机器**：`SCREEN_ENABLED` + `SCREEN_DEDICATED_MACHINE` 双门——主机名比对
   （不区分大小写，Windows 主机名书写习惯），**声明为空 = 没有任何机器被声明 = 永远
   拒绝**（fail closed）。拒绝原因一律是短 token（`screen_disabled` /
   `screen_machine_undeclared` / `screen_machine_mismatch`），不携带任何画面信息。
2. **画面单向进模型**：tile 经宿主 `SCREEN_INBOX`（有界、TTL、新帧覆盖旧帧、消费一次
   即走）在 `ScreenFrameStage`（紧贴 ModelStage 之前）写入 `ctx.extras
   ["clean_segments"]`——`ModelStage` 读图像的既有缝，**已归档的 event.segments 零变化**
   （像素不进 messages 表）。全模块无一处文件写入；测试钉住帧字节不出现在审计/日志/
   异常文本（§1.3 零命中门槛）。
3. **配额**：`Capability.SCREEN` 入 `SENSITIVE_CAPABILITIES`——插件路径直接继承 guard
   的 30 次/分钟敏感滑窗；每次请求帧数被 `SCREEN_FRAMES_MAX`（≤6）钳制。
4. **只看不碰**：`screen/capture.py` 无任何输入注入；依赖只有抓屏用的 mss（可选
   extra `soapbot[screen]`，懒加载，同 edge-tts 措辞）与既有 Pillow。**没有** pyautogui、
   没有键鼠通道——控制面第二阶段另开设计。
5. **会话可见性**：审计只记 frames/used/dropped/duration_ms/bytes 与 session，成功与
   拒绝都进审计；面板可见。

两个入口：四端任一端发 `/look [帧数]`（宿主命令，抓帧后**不短路模型**——命令产出物是
上下文不是文本，模型带着图回答用户的问题）；插件经 `screen.capture` 能力申请
（`ctx.screen_capture(frames)`），拿到的只有 ref + 元数据，帧由宿主在同一轮模型调用前
注入。`_tile`/`_frame_signature` 从 `ai/vision.py` 提升为公开函数（`tile_frames` /
`frame_signature`），GIF 路径与屏幕路径共用同一套拼图与去重阈值。

**接线注意**（写给将来动这块的人）：插件命令的回复会短路模型（`PluginCommandStage`
设 `skip_model`），所以帧注入不能挂在命令阶段里，必须是独立 Stage 且紧贴 ModelStage
——这个顺序进了 `core/trace.py` 的 `STAGE_ORDER`，被两个测试钉住。
