## 2. 吸收清单（三项，均为设计增补，不新增代码）

1. **长会话交接**（篇 09）：插件 worker 是常驻进程，会话上下文满了之后的行为目前
   未定义。soapbot 的对应物是「worker 重启即失忆」——可接受（worker 无状态化是
   既有设计），但 auto-chat 这类攒状态的插件（话题片段、计数）需要定义**重启后的
   语义**：storage 已持久化的部分继续有效，内存计数归零并如实向用户报告。登记为
   auto-chat 0.3.0 的行为说明。
2. **假完成识别**（篇 10）：审批总线记录的是「操作者批了什么」，但没有识别「被批的
   任务真的做完了吗」。soapbot 的对应面是 plugin cron 任务与长驻审批——设计增补：
   审批记录增加 `done_at`（插件用 `ctx.storage` 标记完成，面板可见），超时未标记的
   审批在面板标「未确认完成」。实现归属面板（下批）。
3. **批量改文件纪律**（篇 15）：插件通过 storage/http 没有批量写宿主文件系统的面
   （写入面为零，天然安全）——**本仓库不需要**；该纪律记给未来若开放「插件批量
   生成文档」类能力时参考：先写临时区、逐个校验、失败整体回退、每文件一行审计。

## 3. 与本仓库立场不同、不吸收的

- 篇 02 的「管家会自己重启服务」：本仓库巡检**只读**是刻意的（见 docs/operations.md
  与 plugin_worker_guard 的自述）——「列表变了就删掉正在跑的东西」本身是故障。
- 篇 07 的「自动动作分级放行」阶梯里最高档（无人值守执行）在 soapbot 没有对应物：
  插件的一切出站动作都要过 capability 白名单，不存在「最高档」。
